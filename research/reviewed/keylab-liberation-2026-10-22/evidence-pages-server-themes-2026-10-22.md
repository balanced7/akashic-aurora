## 1. Piano server (port 8793)

- Launch: `py -m arsenal serve [--port 8793] [--root ...] [--performance-root ...] [--no-performance-log]`, parsed in `arsenal/__main__.py:13-21`. Also registered as a dev-server config `"arsenal-web"` in `.claude/launch.json:12-22` (this repo's own Claude-Browser launcher, not a Daniel-side supervisor).
- Routes (`arsenal/serve.py:286-360`): GET `/` →302 `/first-light`; GET `/first-light`, `/play`, `/piano` (static HTML, `:295-300`); GET `/web/*` passthrough under `arsenal/web/` (`:301-302,385-389`); `/api/health`, `/api/midi/ports`, `/api/library`, `/api/resolve`, `/api/takes`, `/api/presets`, `/api/piano/cues` (SSE), `/api/piano/cues/status`, `/api/piano/looks` (GET/PUT), `/api/piano/{replay,deck,jam}...` (jam API), `/api/performance[...]` (practice log), `/api/media/<id>`, `/api/probe/<id>`, `/api/analysis/<id>`, `/api/graph/<name>`, `/api/take/...`; POST `/api/plan`, `/api/recordings`, `/api/piano/cue`, `/api/edit/*` (→`arsenal/media/editapi.py`, `:283-285`).
- Pages served: `/piano`→`arsenal/web/piano.html` (+`piano.js`/`piano.css`); `/first-light`→`first-light.html/js/css`; `/play`→`play.html/js/css` (all `arsenal/serve.py:295-300`, files in `arsenal/web/`).
- **"VFX Bench" and "Shader Lab" are NOT served by this server.** VFX Bench = `scripts/vfx.html`, served by a *different* process, `scripts/bifrost_ui.py` at route `/vfx` (`scripts/bifrost_ui.py:817-818`), configured as `.claude/launch.json` entry `"bifrost-ui"` on port 8790. Shader Lab = `arsenal/web/shaderlab/` (`index.html`, `lab.js`, …), served by yet another standalone server `arsenal/shaders/serve.py` on port 8797, which explicitly refuses port 8793 (`arsenal/shaders/serve.py:4-8,36,59`: `FORBIDDEN_PORTS = {8793: "Daniel's arsenal server"}`). ## 2. MIDI input
- The piano server (`arsenal/serve.py`) does **not** open the KeyLab's MIDI input. `arsenal/midiports.py:1-9` is explicitly read-only (WinMM `ctypes` enumeration only, no port opened) — used only for `GET /api/midi/ports`.
- Actual key/pedal/CC input is **Web MIDI in the browser**: `arsenal/web/piano.js:3801` `navigator.requestMIDIAccess({sysex:false})`; handler bound at `piano.js:3852` (`input.onmidimessage = onMidiMessage`), dispatch at `piano.js:3870`. Port matching: `isKeyLabKeys` regex `/keylab/i` and not `/daw/i` (`piano.js:3779`); ranking prefers a name matching both `/keylab/i` and `/midi/i` (`piano.js:3796-3797`). Port names: `"KeyLab 88 mk3 MIDI"` (keys/pedal/CC) vs `"...DAW"` (`piano.js:3776-3777`).
- Exclusivity: no code claims exclusive access. The module manifest `arsenal/modules/webmidi.input.json:14` states "Windows MIDI Services lets several apps share the port." A second process using the **legacy WinMM** API (as `arsenal/keylab/winmidi.py:183` `midiInOpen` does) is a different driver model from Web MIDI/Windows MIDI Services; nothing in the repo tests or documents whether a WinMM `midiInOpen` and a browser's Web MIDI session can hold the same port concurrently — `arsenal/keylab/README.md:62` says exactly this is "Not yet tested with a receipt."
- Practice-log / receipt-time: commits `cf166b09` (RED, test) and `0f27a7a3` (GREEN) changed `arsenal/web/piano.js` so `onMidiMessage` computes `eventLagMs = performance.now() - ev.timeStamp` and backdates only the *log* stamp (`tLog = t - lag/1000`), leaving on-screen animation at `t = clock()`. Lives in `piano.js` around the `onMidiMessage` function (`piano.js:3870`+, referenced again at `piano.js:2699`). Test: `tests/piano_receipt_time.test.mjs`.

## 3. Live state channels today
- **SSE**, not WebSocket (grepped `arsenal/web/*.js` for `new WebSocket` — zero hits). `GET /api/piano/cues` (`arsenal/serve.py:607-652`) is a long-lived `text/event-stream` connection held on its own thread; client opens it via `EventSource` at `url: /api/piano/cues?caps=jam1,deck1&page=<id>` (`piano.js:3451`). Server→page push only.
- `POST /api/piano/cue {"cue": {...}}` (`arsenal/serve.py:578-605`, validated by `arsenal/pianocue.py`) publishes a cue to that hub — the existing "push a message into the page" path, loopback-origin-checked only (403 off-machine).
- Jam/deck state: `/api/piano/{jam,deck,replay}` routes handled by `arsenal/jam/runs.py` `JamApi` (`arsenal/serve.py:654-679`, wired in `arsenal/serve.py:173`).
- Practice log: `POST /api/performance/open|<session>/events|<session>/close`, `GET /api/performance/<session>` (`arsenal/serve.py:325,352-357,543-575`) — JSON batches with `seq`/`last_seq` dedup, documented in `PIANO-V2-SPEC.md` section 4.
- Saved looks: `GET/PUT /api/piano/looks`, revisioned JSON (`rev`, `presets`), contract in `arsenal/pianolooks.py:1-20`.
- No existing message says "fader moved" or "set pad N colour" anywhere in this server; a KeyLab Control Center would need a new channel (new SSE caps token, or a new route) — nothing today carries hardware-control state.

## 4. Themes / looks / presets
- Palette is **computed (OKLCH)**, not a static table: `noteColor()`/`noteLch()` in `arsenal/web/piano.js:380-398` (OKLCH→linear sRGB, pitch-class or velocity or mono mode). Mode stored in `localStorage` key `arsenal.piano.colour` (`piano.js:324-325`).
- Theme/"Environment" choices actually in code (`arsenal/web/piano/looks/registry.js:123-127`): `moon`="Moonlit lake", `ember`="Ember sanctuary", `nebula`="Velvet nebula", `winter`="Winter mountains", `rain`="Rainforest at midnight", `city`="City of light". **"Aurora Void" does not exist in any code file** — grepped the whole repo; it appears only in the `research/reviewed/keylab-liberation-2026-10-22/*` and `docs/library/design/20261022_keylab-lit-vision-v2_c76424.md` vision/brief documents, i.e. it is a proposed name from this same KeyLab design effort, not a shipped theme. Likewise "Velvet sky" isn't literal — the real id is `nebula`/"Velvet nebula" (commit `c24a490c` message also says "Velvet nebula sky").
- "Patch-bay" identity: CSS comment in `arsenal/web/piano.css:2-5`, `arsenal/web/play.css:2-3`, `arsenal/web/first-light.css:2-3` — tokens defined as CSS vars in `piano.css:7-21` (`--ground #0F1114`, `--panel #171A1F`, `--ink`, `--accent #F0A443`, `--audio #4CC2BA`, `--control #E47FA7`, `--rec #FF4D5E`), referencing "FIRST-LIGHT-SPEC.md 'Look'" (section at `arsenal/FIRST-LIGHT-SPEC.md:251`).
- "Studio Glass" is commit `c24a490c`'s own description of a menu it added for the glass-piano instrument's look choices (`GLASS_LOOKS` object, `arsenal/web/piano/instruments/glass-piano.js:701` and its `Studio` select at `glass-piano.js:2644`) — a per-instrument shader-look picker inside the Studio drawer's Instruments panel, not a separate app menu.
- Preset save/load: `GET/PUT /api/piano/looks` → `state/arsenal/looks/presets.json` (git-ignored), written via a temp-file + `os.replace` (`arsenal/pianolooks.py:18,204-219`). Format: `{"api","rev","presets":[{"id","name","settings":{...},"favourite","created","updated"}]}`, ≤100 presets (`pianolooks.py:12-14,37`).

## 5. Existing menu system
- `arsenal/web/piano/studio/studio.js` implements "the Studio drawer," a right-edge panel with tabs `Practice`/`Looks` (`studio.js:50`), keyboard shortcuts (backtick toggles, PageUp/Down, Home/End, Insert/Delete — `studio.js:51-56`), and a `Looks` tab organized into groups `Scene`/`Atmosphere`/`Colour & numbers`/`Frame` (`studio.js:67-73`) driven by the declarative setting list `LOOK_SETTINGS` in `arsenal/web/piano/looks/registry.js:107-177` (each entry: id, group, label, type, values/options, read/apply). This registry-driven structure (group → ordered settings, each with a label and value list) is the natural source for mirroring a menu onto the KeyLab's LCD.

## arsenal serve verb / service pattern
- `py -m arsenal serve` is the only "serve" subcommand under `arsenal/__main__.py` (`:17-21`); `arsenal/shaders/__main__.py` provides a second, separate `shader serve` (port 8797, default in `arsenal/shaders/serve.py:60`). No unified multi-service supervisor exists.
- The only process-launcher convention found is `.claude/launch.json` (schema used by this session's Browser-pane `preview_start`): two entries, `"bifrost-ui"` (`py scripts/bifrost_ui.py --port 8790`) and `"arsenal-web"` (`py -m arsenal serve --port 8793`) — `.claude/launch.json:1-22`. No Windows Scheduled Task, NSSM, or other OS-level service-supervisor file was found for these servers (searched `*.ps1`/`schtasks`/`nssm` across the repo; only hit was `scripts/ops/install_wake_daemon_task.ps1`, which installs a scheduled task for the *Bifrost agent-mail wake daemon*, unrelated to the piano/shader/vfx web servers). So today each web service (8793, 8797, 8790) is started manually or via this `launch.json`, and kept alive only by whatever process started it — there is no existing "house service" launcher pattern a KeyLab Control Center could join; one would need to be designed.
