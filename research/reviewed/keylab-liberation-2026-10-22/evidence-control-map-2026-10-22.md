# Evidence: the KeyLab 88 mk3 control map in DAW mode (2026-10-22)

The final report of a read-only Explore agent (sonnet), dispatched by Vandor for the A16 design docs
(faders and knobs on shader parameters, dial and fader scrolling, the mode-pin combo, the preset maker,
the FL handoff script). Its source is Arturia's FL Studio script on Daniel's machine, read for facts
(control numbers, screen ids); no Arturia code is copied here or into the repo. Persisted unedited per
the full-fidelity rule; the agent's own UNCONFIRMED marks are kept.

---

All facts below come from Arturia's own shipped FL Studio script at `C:\Users\L5\Documents\Image-Line\FL Studio\Settings\Hardware\Arturia KeyLab mk3\` (located via `py agent_cli.py find KL3`), cross-checked against the arsenal/docs sources you listed. CC/status numbers are decimal unless noted. All CC and pitch-bend traffic arrives on MIDI channel 1 (status 176=0xB0, 224=0xE0); pads arrive as Note On/Off on channel 10 (status 153/137 = 0x99/0x89).

**1. Control-surface messages (DAW mode)**
- Faders 1–8: CC 105,106,107,108,109,110,111,112 — absolute, `value=hw/127` (KL3Process.py:130-139 FADER_MAP; KL3Plugin.py:1072-1076). Fader 9/master: CC113, absolute (KL3Process.py:319,742-744). Fader touch (capacitive, boolean) 1–8: CC 28,29,30,31,33,34,35,36; fader-9 touch: CC37 (KL3Process.py:152-161,320).
- Encoders/knobs 1–8: CC 91,92,94,95,96,97,102,103 — relative, signed-offset-64 (`delta=(value-64)/100` or `/20`; KL3Process.py:119-128; KL3Plugin.py:1108; ArturiaCrossKeyboardKL3.py:34-54). Knob 9/master: CC104, same relative encoding (KL3Process.py:321,750-752). Knob touch 1–8: CC 8-15; knob-9 touch: CC38 (KL3Process.py:141-150,322).
- Main dial (the big clickable jog wheel): **turn = CC116**, relative/signed, but the script only sees values in two narrow bands (65–72 = CW, 55–63 = CCW) which it collapses to fixed steps 64/62, explicitly disabling acceleration ("No acceleration with the main encoder", KL3Process.py:305,334-338,494-500). **Click = CC117** ("SwitchWindow"), fires on press only (filter semantics in KL3Dispatch.py:22-36; KL3Process.py:304,446-456) — opens the focused plugin GUI / arms the mixer track / enters Analog Lab depending on focus (PDF guide p.4,6).
- Transport: Start CC21, Stop CC20, Record CC22, TapTempo CC23, Metronome CC27, Loop CC24, Rewind CC25, FastForward CC26, Back CC40, Save CC41, Quantize CC42, Undo CC43, Redo CC44 (KL3Process.py:291-303,612-880). Several fire only on release (`ignore_press`: Start/Record/Metronome/Loop) and some only on press (`ignore_release`: Undo/Redo/main-dial click) — see filter list KL3Process.py:280-332.
- Context/screen buttons 1–8: CC 45-52 → Device-focus, Mixer-focus, Prev pattern/preset, Next pattern/preset, Mute, Solo, no-op, Arm (KL3Process.py:306-313,549-608; confirmed in PDF guide p.5).
- Pads: Note On/Off ch.10; Bank-DAW pads double as a 32-step sequencer (pads 1-8=steps, 9-12=page select) via OnSeqEvent/SequencerPage (KL3Process.py:350-422,1046-1058; PDF p.5). Mod wheel = CC1, pitch bend = status 224, both routed through the same OnWheelEvent handler and forwarded to virtual port 10 only for Arturia/V-Collection plugins (KL3Process.py:283,330,367-378). **UNCONFIRMED**: no code anywhere in this script reads poly/channel aftertouch (status 0xA0/0xD0), so pad pressure is not consumed here even though the device JSON claims pressure-sensitive pads.

**2. Mode-pin combo / Shift**
A case-insensitive grep for "shift" across every `.py` file in the script folder and across the official PDF guide returned zero hits — Arturia's FL integration never uses a Shift combo for anything. `LedId.py:23-58` enumerates all 34 buttons with LEDs and has no Shift entry. The buttons never wired into KL3Process.py's CC dispatcher (lines 280-332) are Hold, Chord, Scale, Arp, BankP, BankM, Settings, Prog, MIDI, TranspM, TranspP, OctM, OctP — none of their CCs appear anywhere in the script. Of these, BankP/BankM/Settings/Prog/MIDI/TranspM/TranspP/OctM/OctP are the safest "mode pin" candidates (pure navigation/global controls); Hold/Chord/Scale/Arp are riskier since they may still alter note output locally in firmware regardless of DAW mode (UNCONFIRMED from source alone). The one combo Arturia's guide documents, "Prog + Arturia" (PDF p.6, for entering "Arturia Mode"), has a matching `ArturiaConnexion`/`ArturiaDisconnection` SysEx defined in KL3Connexion.py:17-23 that is **never called** anywhere in the script tree (grep confirms) — so avoid Prog, but that particular handoff is firmware-side, not this script's doing.

**3. LEDs**
Every non-pad LED (all 34 button ids, LedId.py:23-58, including Contextual1-8) uses the identical `eSetLed` SysEx as the pads (ParamId.py:28) — i.e. full independent-RGB, not mono-only. Proof: Play is lit green `[0,0x7F,0]`, Record red `[0x7F,0,0]`, Loop/Repeat amber `[0x7F,0x48,0]` (KL3Return.py:96-199,235-251), while Stop/Tap/Save/Quantize/Undo/Redo/Context1-8/Back are simply sent as grayscale triples by this script's own convention, not a hardware limit. Pad ids 34-93 (banks A/B/C/D/DAW) use the same mechanism (LedId.py:59-118).

**4. LCD**
`ScreenId.py:23-74` enumerates 47 layout ids; `KL3Display.py` implements exactly: Properties(0), 1-line(10)/inverted(11), 2-line(12)/inverted(13)/big(14), icon+1-line(15)/icon+2-line(16), 1/2/3-line popups(23/24/25), icon popups(26/27), **knob-graphic(28)**, **fader-graphic(29)**, **pad-graphic(30)**, full popup+icon(31) (KL3Display.py:101-376; dispatch table KL3Pages.py:49-227). Lines are ASCII capped at 32 bytes, truncated to length-4 + "..." (KL3Display.py:36-56); colour is a type byte (0/1) plus an RGB triple 0-127 (e.g. KL3Display.py:107-108). The knob/fader/pad layouts carry one `hw_value` byte (0-127) that draws a live bar, fed from `plugins.getParamValue()*127` / `mixer.getTrackVolume()*127` (KL3Display.py:307-353; KL3Navigation.py:48,70,120-142). **Arturia's script never draws a list/menu**: `eScreenListSetup/Append/Prepend` (20-22), `eScreenBrowser`(40), `eScreenColorPicker`(39), `eTypeCarousel/eInstrumentCarousel`(18-19) exist in the enum but `KL3Display.py` has no method for any of them; browsing stays in FL's own on-screen UI with only a one-line hint pushed to the LCD (KL3Navigation.py:271-301).

**5. Soft takeover / feedback**
No pickup/soft-takeover for faders: a fader always jumps the plugin parameter straight to `hw_value/127`, even far from the parameter's current value (KL3Plugin.py:1072-1076). Encoders are hardware-relative so no takeover applies, but on touch-down the script re-baselines its internal `ABSOLUTE_VALUE` to the plugin's live value (a rebase, not a dead-zone catch-up; KL3Plugin.py:1079-1106). Parameter feedback to the device is real, two-channel: (a) the LCD gets the param name + formatted value string + 0-127 bar via Screen_K/Screen_F (KL3Plugin.py:1086-1090 → KL3Display.py:307-336); (b) each knob/fader slot (index 0-7) gets an `eProperties` connect(0x01)/disconnect(0x00) SysEx on touch/release (KL3Plugin.py:1083,1129), likely driving a per-control link indicator.

**6. Handoff**
`OnInit` sends `eDaw/eConnection=1` the instant FL loads the script and shows "Connected" on the LCD; `OnDeInit` sends `eDaw/eConnection=0` on unload (device_KL3.py:83-100,120-125; KL3Connexion.py:25-31). A second, independent script bound to the keyboard's other port ("KeyLab xx mk3 MIDI") just forwards every CC to virtual port 10 for Analog Lab/V Collection (`device_KeyLab mk3 MIDI.py:1-41`) — DAW control and Arturia-plugin control run on two simultaneous ports, not one toggled mode. The matching `eArturia` connect SysEx is defined but has no caller in this script (point 2) — UNCONFIRMED how firmware itself flags that transition beyond what's in these files.
