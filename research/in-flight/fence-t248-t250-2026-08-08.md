**2. THE COMPARISON `r == (by or t.get("owner"))`**

Line 295:

```python
if is_load_bearing(t.get("files")) and (not r or r == (by or t.get("owner"))):
```

`r` is `reviewed_by or t.get("reviewed_by") or ""` (‑293).  

`(by or t.get("owner"))` evaluates to:
- `by` if `by` is truthy (non‑empty string),
- else `t.get("owner")` (which may be `None` or `""`).

When `by` is **empty** (the default in all convenience wrappers, ‑332‑341), the comparison becomes `r == t.get("owner")`. If `owner` was never set — `propose` default `""` (‑215) — then `r == ""`.  

**Can `owner` make the gate pass when it should not?**  
Yes. If `owner` is `""` (or `None`), then any non‑empty `reviewed_by` ≠ `""`/`None`, so `r == (by or owner)` is `False`, the condition fails, and the gate does **not** require an independent reviewer or `self_verified`. The task closes with a reviewer string that the code considers “someone else,” even if it is in fact the same person with a typo or fake name. The field `by` would be empty, so the gate cannot know who the closer is; it assumes an empty‑string closer is not the reviewer.

**Exact values compared when `by` is empty and `owner` is `None`:**
- `r` = `"some_reviewer"`
- `(by or t.get("owner"))` = `(None)`  (because `"" or None` → `None`)
- `"some_reviewer" == None` → `False` → gate passes.

**CHECK**: create a task without setting `owner` (or `owner=""`), call `done` with `reviewed_by="myself"` and default `by=""`; verify the gate does not raise.

**3. FALSE REFUSALS**  

A false refusal would be a task that **should** close but is now blocked. The gate solely blocks when:
- `is_load_bearing` is true, **and**
- `reviewed_by` is empty **or** equals the closer ( `by or owner` ), **and**
- `self_verified` is empty.

**Concrete scenario that could be a false refusal** (although arguably intentional):
- A task’s closer (`by`) is the same string as the `reviewed_by` because the *reviewer’s agent id* happens to be identical to the closer’s id, but they are two different humans/roles. This would be a name collision; the gate does not distinguish identity beyond string equality.  
- A non‑code change task (e.g., configuration tweak, documentation) that touches a file under `core/` but doesn’t alter logic. The gate treats any file under `core/` as load‑bearing, so a purely cosmetic PR could be blocked. However, that is a policy definition, not a logic bug.

No clear **unintended** false refusal emerged from the code alone; the gate behaves as described. The only tasks that “should close and now cannot” are those where the closer is also the reviewer *and* the work should be considered self‑verified but the caller accidentally omits `--self-verified`. That is a missing flag, not a gate defect.

**CHECK**: attempt to close a load‑bearing task with `by="claude", reviewed_by="claude", self_verified=""`; the gate raises → must pass `self_verified` to proceed.

**4. `is_load_bearing` PATH NORMALISATION**  

Defined at ‑129‑135:

```python
def is_load_bearing(files) -> bool:
    for f in (files or []):
        p = str(f).replace("\\", "/").lstrip("./")
        if any(p.startswith(prefix) for prefix in LOAD_BEARING):
            return True
    return False
```

**What it does** (and does not do):

| Input example | After `replace("\\", "/").lstrip("./")` | Does it start with `"core/"`? | Conclusion |
|---------------|-------------------------------------------|-------------------------------|------------|
| `core/module.py` | `core/module.py` | Yes | load‑bearing |
| `.\core\module.py` | `./core/module.py` → after lstrip `core/module.py` | Yes | load‑bearing |
| `/app/core/module.py` | `/app/core/module.py` → lstrip removes `/` → `app/core/module.py` | No (`app/…`) | **NOT** load‑bearing |
| `sub/../core/x.py` | `sub/../core/x.py` (no leading `./`) | No | **NOT** load‑bearing |
| `core.py` (root) | `core.py` | No (prefix is `core/`, not `core.`) | **NOT** load‑bearing |
| `mycore/some.py` | `mycore/some.py` | No | **NOT** load‑bearing |
| `../../core/x.py` | after lstrip `core/x.py` | Yes | load‑bearing (by accident) |

**Key weaknesses**:
- **Absolute paths** are stripped of the leading `/` but the remainder starts with `app/` (or whatever the first directory is), so they escape.
- **Non‑leading `..`** segments are not resolved, so paths like `subdir/../core/…` are invisible.
- **Backslashes are handled**, but the function never calls `os.path.normpath` or resolves real paths; it relies on a simple string prefix check after minimal cleaning.
- **A file at the repo root named `core.py`** is not caught because the prefix is `"core/"`.  
- **Directories with names *ending* in `core/`** (e.g., `mycore/`) are also missed.

**CHECK** for each: instantiate and print `is_load_bearing(["the_path"])` for the listed examples.

## 1. NEW BYPASSES INTRODUCED BY THE FIX ITSELF

`is_load_bearing` normalises by stripping `../`, backslashes, leading `/` and `./`, then matches on **path segments** (line 145–159). No Unicode normalisation is performed.

**Path that SHOULD be load‑bearing but is no longer caught**  
A homoglyph‑encoded variant of a `LOAD_BEARING` directory, e.g. `"сore/safety.py"` where the first `с` is Cyrillic U+0441 instead of Latin `c`. The prefix `"core/"` is split into `["core"]`; the Cyrillic path yields `["сore", "safety.py"]`. Because segment equality is strict, no match occurs. The declared file bypasses the review gate, even though the real file on disk could be the ordinary `core/safety.py` if the agent writes the original path in `files` but edits the real file. (The gate is documented as a speed‑bump, not a wall – line 135‑137 – but this is still a bypass introduced by the segment‑matching algo.)

**Path that should NOT be load‑bearing but now is**  
I found no instance where the segment‑equality logic incorrectly flags a non‑target. For example:
- `"core.py"` → segs `["core.py"]`; no match on `["core"]` because it looks for the exact segment, not a substring.
- `"score/file.py"` → segs `["score", "file.py"]`; `"core"` not found.
- Trailing slash on a declared file, e.g. `"core/"`, becomes `"core"` after `normpath` → segs `["core"]`; correctly matches.

Thus the only new bypass is the Unicode‑homoglyph avenue.

**CHECK**: In Python, `is_load_bearing(["сore/test.py"])` returns `False` because the first character differs. Add `from task_ledger import is_load_bearing; print(is_load_bearing(["сore/test.py"]))` to confirm it returns `False`.

## 2. THE IDENTITY COMPARISON

Lines 320‑321 compute `closer = (by or owner).strip()` and `same = bool(r) and bool(closer) and r.casefold() == closer.casefold()`.  
`str.casefold()` uses Unicode case‑folding, which is more aggressive than `lower()`.

**Pair of distinct real identities that become equal**  
- `"Straße"` (German street) and `"STRASSE"` (uppercase) both casefold to `"strasse"`, so they appear to be the same reviewer.
- Likewise, any names that differ only by case and certain Unicode foldings (e.g. Greek final sigma) will be considered identical.

**Single identity that it makes unequal to itself**  
- A name composed of precomposed vs. decomposed Unicode forms, e.g. `"Ana\u0303"` (U+0061 U+0303) vs. `"Anã"` (U+00E3). `casefold()` does **not** perform Unicode normalisation, so the two representations remain different strings. The same actual person could be stored inconsistently and then not match themselves.

**CHECK**: Run `print("Straße".casefold() == "STRASSE".casefold())` → `True`. Run `print("Ana\u0303".casefold() == "Anã".casefold())` → `False`.

## 3. THE UNKNOWN‑CLOSER REFUSAL

Lines 326‑330 introduce a new block **inside** the `to == DONE` path, **before** the main independence check:

```python
if is_load_bearing(t.get("files")):
```

This fires when:
- the task touches `LOAD_BEARING` paths, **and** no `--by` is given, **and** the task has no `owner`, **and** no `--self-verified` reason is supplied.

**A legitimate close that used to succeed now fails**  
Previously, if a load‑bearing task had a **reviewer** (`r` non‑empty) but the closer was unknown (no `by`, no `owner`), the old independence check would not block:

- `same` = `False` (because `closer` empty → `bool(closer)` is `False`).
- `not r` is `False` (since `r` is non‑empty).
- Condition `(not r or same)` = `False`, so no error was raised.

Under the new code, that exact scenario hits the unknown‑closer refusal **regardless** of the reviewer, and the close is rejected. For example, a script that closes a load‑bearing task with `--reviewed-by Alice` but no `--by` or `--self-verified` would now fail. Non‑load‑bearing tasks are unaffected because the refusal is guarded by `is_load_bearing`.

## 4. ORDERING OF THE TWO `is_load_bearing` CHECKS

The two checks are at line 322 and line 331, both inside the `to == DONE` block. They examine the same `t.get("files")` and call the same pure function `is_load_bearing`. The files list is not mutated between the two calls. Therefore they **cannot disagree** – if the first returns `True`, the second will also return `True`.

If, hypothetically, they could differ, the consequence would be: after passing the first gate (the unknown‑closer refusal), the second gate might still block the close for independence reasons, or vice‑versa. But in the actual code this is deterministic.

**CHECK**: The code contains no assignment to `t["files"]` between lines 322 and 331; the function is stateless, so a second call with identical arguments must produce the same result.
