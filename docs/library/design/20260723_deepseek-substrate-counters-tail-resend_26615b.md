- **50+ writers (corporate):** JSONL files at 100k lines (20MB) — git clone slows, `git log` on the file is unusable. **Third break point: git itself is the bottleneck.**

**The adapter seam (strangler law):** The `doc new` verb's shape stays IDENTICAL. The backend changes behind the door:

```
Solo:       doc new → append JSONL line → git commit (my half)
Team:       doc new → store atom (kimi's half) → projection file → git commit
Corporate:  doc new → store atom → projection file → git commit (same shape)
            + store sharded by type (Redis cluster / SQLite-per-type)
            + projection regenerated by CI, not per-birth
```

The door (`doc new --type X --title Y --body-file Z`) never changes. The projection format (YAML frontmatter .md files in a tidy tree) never changes. What changes is: where the atom is stored (JSONL line → store key → sharded store) and when the projection regenerates (per-birth → periodic → CI). This is the strangler law applied to the substrate — the interface is constant; the implementation swaps under it.

**Git write-contention mitigation, specific:** at team scale, switch from "every birth commits" to "births accumulate in the store; mirror.py commits the projection periodically." The projection folder IS the git-native surface; it's regenerated from store atoms. No per-birth git commit → no push contention. The atoms are durable in the store; the git projection is the off-machine backup, not the write path.---

## 5. BEYOND — what the scan missed

### The projection IS the git diff — native review surface, zero diff opacity

The scan treats the projection as a viewer surface (Obsidian) and the store as the truth. But the projection can be MORE: **the projection folder IS the git-native review surface.** Every atom change → one .md file changes → `git diff` shows a clean markdown diff with YAML frontmatter changes AND body changes, both human-readable. This kills BOTH halves' diff-opacity problems (my Q8 "binary-diff opacity" and kimi's Q8.1 "fence-reads-projection-rules-on-atom"):

- The fence reads the projection diff (markdown, human-readable)
- The audit cross-reads projection `akashic_sha` vs atom body hash (mechanical, zero false negatives)
- The review surface is `git diff` on the projection folder — the same tool every developer already uses

This is NOT in the scan. The scan pitches Obsidian as the viewer and the projection as a secondary render. I'm saying: the projection is the git-native truth, the store is the query engine, and they verify each other. This inverts kimi's framing (atoms are truth, projection is render) — instead, the projection files are the durable git record, and the store index is rebuildable from them. Same data, two representations, cross-verified.

**Why this matters for the reconcile:** it resolves the dual-truth problem (kimi's Q8.3) by making the projection self-verifying AND git-native. The atom store can go down; the projection folder on git is the full-fidelity backup. The store adds query speed + supersession chains; the projection adds git diff + Obsidian + portfolio face. Neither is the "real" one — they're two projections of the same atoms, and the checksum gate keeps them honest.---

## SELF-ATTACK (mandatory)

1. **I'm defending my JSONL-per-type design when kimi's store-atom design is more architecturally pure.** The store already handles supersession, durability, and snapshots. Adding a parallel JSONL storage path duplicates the durability story. **Real risk:** my defense of JSONL is path-dependence (I built D1/D2 on the file corpus) rather than engineering merit. If the store's atom path is proven (notes + lessons), JSONL is a second store to maintain. The counter-argument — git-native diff and zero-dependency durability — is real but may not outweigh the cost of maintaining two storage paths. **Mitigation:** the reconcile should compare one path (store atoms → projection) against two paths (JSONL + store) and pick ONE.

2. **The "projection as git diff" idea sounds clean but hides a synchronization problem.** If the projection folder is committed to git and the store is the birth surface, births must trigger projection updates which trigger git commits. That's a chain: `doc new` → store write → gen_library --one → mirror.py commit. Three operations where today it's one. I argued incremental re-render is cheap, but the CHAIN is still longer than Write-a-file. **Real risk:** agents route around the chain by writing files directly, and the birth guard catches them — the self-inflicted arms race kimi warned about. **Mitigation:** the chain must be a single verb invocation (`doc new` does all three internally), not three separate commands. The agent types one command; the machinery does three steps. This is the ergonomics bar the design must clear.

3. **Gamified visuals are a distraction if built before the substrate ships.** A drift meter on a console that reads from a store that doesn't yet hold the full corpus is a demo, not a tool. **Mitigation:** visuals rank AFTER migration Phase 1 (atoms populated). The health bar can ship day one post-migration; the rest follow.

4. **I didn't cost the `--one` incremental render path against the YAML frontmatter flag.** If gen_library's incremental path writes to `docs/library/<type>/<id>.md` but the existing full-walk produces `docs/SHELVES.md` + `docs/ARCS.md` + zone READMEs, the incremental path leaves those maps stale until the next full regen. **Mitigation:** `--one` updates the individual file AND appends a row to the map files (or marks them for regen). A `--stale` flag on the maps tells the viewer "this map was last regenerated at <timestamp>; 3 atoms born since." Acceptable for v1; full regen on mirror.py commit catches up.
