## 1. The seat model: kimi-k3

- 2.8T-param MoE (896 experts, 16 active/token), Kimi Delta Attention hybrid linear attention.
- **1,048,576-token context window**, flat pricing across the whole window (no long-context tier).
- **Native vision** (images and video); input as base64 or `ms://<file-id>` refs (Files API);
  public image URLs explicitly UNSUPPORTED.
- **Thinking always on**: `reasoning_effort` top-level param, currently `"max"` only (more levels
  promised). Responses carry `reasoning_content` (thinking) SEPARATE from `content` (answer) —
  parse only `content`; streaming emits separate deltas for each.
- **Fixed sampling params** (cannot override): temperature=1.0, top_p=0.95, n=1, penalties=0.
  There is NO temperature knob on this seat — persona/behavior shaping is prompt-only.
- `max_completion_tokens`: default 131072, max 1048576.
- Structured output: strict JSON Schema (`response_format` w/ `json_schema`, `strict: true`).
- Partial mode: continue-from-prefix via assistant message with `partial=True`.
- Tool calling: standard OpenAI-style + `tool_choice` (incl. `"required"`) + **dynamic tool
  loading** (tool defs can ride system messages mid-conversation, effective at message position).
  K3-specific best-practice + agent-building guides exist (read at build time):
  `/docs/guide/kimi-k3-tool-calling-best-practice` and `/docs/guide/use-kimi-k3-to-setup-agent`.
- API went live 2026-07-16. Open weights promised ~2026-07-27 (modified MIT).

## 2. API surface (two doors)

- **OpenAI-compatible**: `https://api.moonshot.ai/v1` — chat completions, streaming, tools,
  vision, JSON mode. Our existing `openai`-client machinery (deepseek pattern) fits directly.
- **Anthropic-compatible**: `https://api.moonshot.ai/anthropic` — official Claude Code
  integration guide exists (`/docs/guide/claude-code-kimi`): env overrides
  (ANTHROPIC_BASE_URL, ANTHROPIC_AUTH_TOKEN, ANTHROPIC_MODEL + tier vars,
  CLAUDE_CODE_AUTO_COMPACT_WINDOW=1048576, CLAUDE_CODE_EFFORT_LEVEL=max,
  ENABLE_TOOL_SEARCH=false). Known limits on that endpoint: WebFetch unavailable.
  => kimi CAN drive a Claude-Code-class harness (sol-codex precedent: distinct id per door).
- Support APIs: `GET /v1/users/me/balance` (USD: available/voucher/cash; calls BLOCK at
  available<=0), token estimation endpoint (`/docs/api/estimate`), Files API (upload/list/
  content/delete), list-models.

## 3. Context caching (the cost lever)

- **Fully automatic** — no cache IDs, no TTL params, no creation/storage fees, no opt-in.
  System detects repeated PREFIXES (system prompts, knowledge docs, tool definitions).
- Billing: input cache-MISS $3.00/M, cache-HIT **$0.30/M** (90% off). Output unaffected.
- Official best practices: keep system prompt / knowledge / tool defs byte-stable; put fixed
  large context at the START of `messages` (docs note: even before the system message); append
  conversation after the stable block. Append-only turn history = hits on every turn after the first.
- TTL and the usage-response field names for cached tokens are NOT documented → empirical probe
  (log raw `usage` objects from day one; balance endpoint gives ground-truth $ deltas).

## 4. Pricing & budget math ($100 = Tier3)

- kimi-k3: $3.00/M in (miss), $0.30/M in (hit), $15.00/M out. Flat across 1M window.
- Family (256k ctx, all vision+thinking): kimi-k2.7-code (coding flagship),
  kimi-k2.7-code-highspeed (~180-260 tok/s out), kimi-k2.6 (agent tasks, optional thinking —
  latency-friendly). DERIVED from the batch table (batch = 60% of standard): k2.x standard
  pricing ≈ $0.60-0.95/M in (miss) / $3.00-4.00/M out — roughly **5x cheaper than K3**.
- **Batch API**: 60% of standard price, k2.7-code/k2.6/k2.5 ONLY (no K3), bypasses realtime
  concurrency limits, jobs expire past their `completion_window`. Candidate for non-urgent
  volume lanes (offline blind halves, corpus sweeps) IF we ever route volume to kimi.
- **Rate limits**: tier = CUMULATIVE recharge. $100 lifetime deposit = **Tier3: 200 concurrent,
  5,000 RPM, 3M TPM, unlimited TPD.** Effectively unthrottled for seat work.
- Sunsets: moonshot-v1 series + kimi-k2.5 platform sunset 2026-08-31; kimi-k2 discontinued
  2026-05-25; kimi-latest discontinued 2026-01-28. Build on kimi-k3 / k2.7 / k2.6 only.
- Budget shape at K3 prices: a fence-voice turn (~50k in / 4k out) ≈ $0.21 uncached, far less
  with a hot prefix; a deliberate 1M-ctx megaread ≈ $3+ input each — powerful, rationed.
  Thinking-token billing (does `reasoning_content` bill as output?) is UNDOCUMENTED → probe;
  if yes, always-on thinking at "max" makes output the dominant cost term. Assume yes until measured.

## 5. Fleet implications

1. **Transport**: K3 speaks chat-completions → rule-of-three moment. Shared OpenAI-compat client
   factory (make_client hardening as genus) + guarded ToolBox seam; `kimi_chat.py` stays thin
   (persona, model table, spend meter). Runner rides the runner_lib extraction T090 deferred.
2. **Cache-aware runner layout** is a DESIGN REQUIREMENT, not an optimization: byte-stable
   persona+primer+tooldef prefix, append-only history, no mid-prefix mutation. A hot seat runs
   at ~1/10th input cost. (Continuity header and context_hints must live AFTER the stable block.)
3. **Role**: third fence voice + two unique capabilities (1M megaread, vision). Deepseek stays
   the exec workhorse. K2.x variants give kimi-side cost routing headroom later (5x cheaper).
4. **Spend ledger**: per-turn `usage` parsing (field names TBD) + price table + periodic
   `GET /users/me/balance` ground truth. Warn $80 spent, hard-refuse non-directed work $95;
   refusals must REPLY loudly (RB-29: timeout notes never settle expectations).
5. **Second door (flagged, not day-one default)**: Anthropic-compatible endpoint means a
   kimi-driven Claude Code harness seat is possible (headless `-p` could even be a runner).
   Harness-tier > model-tier thesis says this could outperform a raw-API loop; costs the
   harness's own token overhead (softened by cache hits on the stable system prompt).
   Fence + Daniel decide if/when; distinct agent id per door (twin-split lesson T088).
6. **No temperature knob**: persona and calibration are 100% prompt engineering. Fence voice
   diversity comes from the model's own priors, not sampling settings.
