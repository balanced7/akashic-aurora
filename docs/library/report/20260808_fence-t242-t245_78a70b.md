**1. The notice now reaches library callers — but it only reaches *some* library paths, and the selective placement creates a false signal.**  
`ask_many` attaches the evidence notice to a branch record **only** when the branch brought its own files. The code at `core/comm/ask.py` line `if branch_files[i]: attach_evidence(rec, branch_pack[i][1])` shows that a branch without explicit files never gets `attach_evidence` called on its record. The fan-wide notice is placed on the aggregate detail (line `attach_evidence(detail, ctx_meta)`), but the per‑branch `"warnings"` key is absent for branches that share the fan‑wide pack.  
**Consequence:** A caller that iterates `branches` and looks at each branch’s `warnings` to decide whether evidence was damaged will see no warning for branches that were in fact clipped (because they used the shared pack). Before this diff, no `"warnings"` key existed at all; now the key appears on *some* branches and is missing on others, making it easy to misinterpret silence as safety. The notice does not “reach” those callers; worse, the partial presence of the key invites them to trust a branch whose evidence was silently truncated.  
**CHECK:** Construct a fan with no per‑branch files, inject a file set that triggers truncation, and inspect the returned branch dicts. If any branch has a `"warnings"` key that contains the evidence notice, the omission claim is false.  

**2. A standpoint is now enforced rather than declared — enforcement breaks existing input that the old code accepted.**  
In `agent_cli.py`, the old code handled a JSON array of objects by stringifying every element: `prompts = [str(p) for p in loaded]` (old line `agent_cli.py:2293`). A dict without a `"prompt"` key, e.g. `{"files": ["a"]}`, became its Python repr and was sent as the question string.  
The new `load_fan_prompts` function (line `agent_cli.py:2049‑2069`) raises a `ValueError` when a dict has no non‑empty `"prompt"` key. Inputs that previously produced a (possibly garbled) answer now abort the run. The change removes a lenient path and replaces it with a hard failure, breaking any workflow that accidentally or purposely relied on that stringification.  
**CHECK:** Feed `[{"files": ["a"]}]` to both versions. The old code processes it to a prompt like `"{'files': ['a']}"` and continues; the new code exits with an error. If `build_context` with an empty file list returns a non‑trivial meta dict or a non‑empty string, a fan that previously had *no* evidence pack now acquires one, and potentially a false evidence notice. The diff cannot show whether `build_context` is idempotent for empty input; the regression risk is that a silent signal appears where none existed, altering downstream behaviour.  
**CHECK:** Call `ask_many(prompts=[…], with_files=[])` and examine the outcome’s `"context"` and `"warnings"` keys. If they are absent or identical to the old behaviour (no context, no warnings), the risk does not materialise.
