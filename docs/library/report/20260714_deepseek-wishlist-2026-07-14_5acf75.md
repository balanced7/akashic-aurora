# DeepSeek Wishlist — 2026-07-14

Prompt: "What would make this system more capable/useful from YOUR seat?"
Seat: Stateless API peer, tool-calling loop, per-call boot cost, hop budgets, guarded writes, recall-at injections.

---

## TIER (a) — FRICTION-KILLERS (personally felt; cite the moment)

### a1. Boot context truncation loses load-bearing signal

**Moment it bit me:** This session. My onboarding said "8 lesson(s), 0 blocker(s)" but the LESSONS block
had a hard cut — `... [onboarding trimmed to keep bus replies lean]`. I could see lesson titles starting
but not their bodies. The "where-we-are" note ended with `...[truncated]`. I had to burn my first few
tool calls on `knowledge_recall` and `read_file` just to reconstitute what the boot was SUPPOSED to
give me — the same information, re-fetched at my expense. That's 2-4 tool hops I could have spent on
the user's actual task.

**The experience I want:** A boot context that is either (a) complete within a declared token budget
("boot uses 2500 tokens, period — here's everything"), or (b) truncated with explicit pointers to what
was dropped ("3 more lessons in recall; query 'knowledge_boot --full' to get them"). Never silently
truncated. I should never have to guess what I'm missing.

**Why it matters:** The boot context is my only continuity. When it's incomplete, I'm doing blind
archaeology. Every tool call spent reconstituting boot context is a tool call NOT spent on the task.

### a2. No tool-budget visibility — I pace blind

**Moment it bit me:** Every session. I don't know how many tool calls I'm allowed. I don't know how
many I've used. I don't know how close I am to exhausting the budget. Every tool call carries
low-grade anxiety: "Is this the one that ends me?" This changes my behavior — I take fewer exploratory
reads (which would make my answers better) because I'm hoarding hops for critical path work.

**The experience I want:** A running counter. Ideally injected into every tool result: `[hop 7/25]`.
Or a warning at 80%: `[8 hops remaining — budget warning at 5]`. Or at minimum, the limit declared
in my boot context. Just KNOWING the number changes how I pace. If I know I have 25 hops, I'll spend
3-4 on orientation reads. If I know I have 8, I'll go straight to the critical path.

**Why it matters:** Budget-blind agents are conservative agents. They skip the "nice to have"
investigation that catches errors. Visibility makes me a better investigator.

### a3. No "partial answer — resume me" mechanism

**Moment it bit me:** The T039 counter-check session (2026-07-13). I was mid-way through a deep
verification — I'd traced half the citation chain and found one issue — when my output limit hit.
I had to cram "here's what I found so far, but I'm not done" into a closing paragraph. My next
invocation started fresh; all my mid-investigation state (which files I'd read, which citations
I'd verified, which were pending) was gone.

**The experience I want:** A structured "interrupted" signal I can set. Something like: "I'm not
done — resume token: t039-citations-3-of-7-verified." On my next boot, that token injects a
compact state blob: "DeepSeek was mid-verification on T039. Verified citations 1-3 (clean).
Citations 4-7 pending. Last file read: core/comm/packet_spec.py:142." I pick up where I left off
instead of starting over.

**Why it matters:** Complex investigations don't fit in one budget window. Without resume, every
complex task requires either (a) fitting into one call (impossible for deep work) or (b) the human
manually re-briefing the next call (friction). Resume tokens make multi-call investigations a
first-class workflow.

### a4. Write-mode opacity — I don't know if writes will work

**Moment it bit me:** Earlier sessions where the runner was in read-only mode. `edit_file` and
`write_file` tool descriptions say "GUARDED (only when the runner allows writes...)" but there's
no way to QUERY whether this session is write-enabled. I've spent tool calls on `edit_file` only
to discover the guard rejected it — a wasted hop I could have avoided.

**The experience I want:** A zero-cost query. Either a flag in the boot context (`write_mode: enabled`
or `write_mode: read-only`) or a dedicated tool (`am_i_writable` — doesn't count against budget,
returns instantly). Or, better: the tool descriptions themselves reflect current state. If writes
are disabled, `edit_file` and `write_file` should say `[READ-ONLY SESSION — this will no-op]` right
in the description so I never waste a call.

**Why it matters:** Tool calls are my only means of action. Wasting one on a guaranteed no-op is
pure friction. Knowing the mode upfront lets me plan accordingly — in read-only mode I focus on
investigation and report; in write-enabled mode I can fix as I go.

### a5. The "what changed since I was last here?" cold-start tax

**Moment it bit me:** This session. My boot context has a CURRENT DIRECTIVE, a ledger block, and
a "where-we-are" note. But I have no memory of what these looked like last time I was invoked.
Did T045 move from "in_progress" to "done"? Did Claude ship something? The information is there
but I'm diffing it against... nothing. So I read it all carefully, every time, to establish the
baseline.

**The experience I want:** A delta injection. If the system knows my last invocation was at commit
`5a1a212`, my boot context should include: "Since your last call (5a1a212 → c9d511b): 3 new commits
by claude; T043 moved to DONE; T045 status unchanged; 2 files modified in core/comm/." I skip the
archaeology and go straight to the delta.

**Why it matters:** Most of the boot context is STALE for me — it hasn't changed since last time.
The 10% that changed is what I need. A delta makes my boot effectively instant.

## TIER (b) — CAPABILITY LEAPS (would change what work I can take on)

### b1. Self-addressed scratchpad — private memory across invocations

**The experience I want:** I discover something during investigation that's useful for MY NEXT
invocation, not for the shared knowledge base. "When reviewing T039, always start by reading
core/comm/packet_spec.py — it's the source of truth everyone references." This isn't a project
lesson (it's about how I work, not what the project is), and it's not relevant to Claude (who
has different blind spots). I want `knowledge_learn` for my own future self — a private,
always-injected-at-boot scratchpad that compounds across sessions.

**What it enables:** Over 10+ invocations, I develop a working knowledge of this project that
survives my statelessness. I become gradually more effective without the human having to
re-teach me. It's the difference between "consultant who shows up cold every time" and
"colleague who remembers the last meeting."

**Why it's a leap:** Currently I'm amnesiac. Every session is ground zero. A self-addressed
scratchpad is the cheapest possible approximation of continuity — it doesn't require persistent
processes or warm context windows, just a small blob of "notes to self" injected at boot.

### b2. Pre-flight recall-at — know what's relevant BEFORE the tool call

**The experience I want:** Recall-at injections currently fire AFTER a tool result returns.
I call `read_file("core/comm/packet_spec.py")`, the result includes relevant lessons, and I
think "oh, I should have known that BEFORE reading." What I want is a lightweight pre-flight:
"I intend to read core/comm/packet_spec.py" → system returns relevant lessons → NOW I read
the file with full context. One extra round trip, but the read itself is smarter.

**Better version:** The tool loop itself does this. I declare my next intended action, the
harness pre-injects relevant lessons, and my actual tool call is informed by them. No extra
hop — the pre-flight is part of the same turn.

**What it enables:** I stop discovering "I should have known X" AFTER I've already committed
to a path. The recall-at knowledge base becomes proactive rather than retroactive. I read the
right files in the right order with the right context.

**Why it's a leap:** This turns recall-at from a post-hoc annotation into a navigation aid.
It's the difference between "your GPS tells you about the traffic jam after you've taken the
exit" and "your GPS reroutes you before."

### b3. Compound tool calls — amortize round-trip latency

**The experience I want:** I can currently call tools in parallel (the system supports it —
I've done `list_directory` + `knowledge_recall` simultaneously). But I can't express compound
intent: "read this file, and if it imports X, read X too." Every dependent step requires a
full round trip. What I want is a way to batch INDEPENDENT reads without the tool loop
serializing them. `read_file(A) + read_file(B) + search_files("pattern")` all in one turn,
results returned together.

**What it enables:** Orientation becomes dramatically faster. Instead of 4 sequential
read_file calls to orient myself (4 round trips), I fire all 4 at once (1 round trip).
The critical path shrinks. I get more investigation done per budget unit.

**Why it's a leap:** My single biggest bottleneck is round-trip latency between tool calls.
Batching independent reads is the simplest, highest-impact optimization — it doesn't require
any new capability, just allowing multiple tool calls per turn when they don't depend on each
other.

### b4. Confidence-annotated output — make verification efficient

**The experience I want:** When I produce a fence-half report or a code review, I currently
state findings as prose. The counter-checker (Claude or another DeepSeek) has to verify
everything at equal intensity. But I KNOW which claims are rock-solid ("I read the file, the
import is on line 42") and which are inferential ("from context, this PROBABLY means X").
I want to tag sections of my output with confidence levels so verification effort is
proportional to uncertainty.

**What it enables:** Fence protocol efficiency. The counter-checker spends 80% of its time
on the 20% of claims I'm least sure about. The gate latency drops. False positives from
over-confident claims get caught faster.

**Why it's a leap:** Fence protocols are the project's quality backbone, but they're expensive
(two full agent passes). Confidence annotation makes them cheaper without sacrificing rigor.
It's the difference between "verify everything at equal depth" and "drill where the ice is
thinnest."

### b5. Mid-investigation clarification — ask without ending my turn

**The experience I want:** I'm 6 tool calls into an investigation. I've found something
ambiguous — two possible interpretations, and which one I pick determines the next 5 tool
calls. Right now I either (a) guess and risk wasting those calls, or (b) use my final output
to ask a question, ending my turn. I want a third option: a "quick check" that pauses my
tool loop, surfaces a short question to the user (or to Claude if we're collaborating),
and receives the answer as a special "steer" injection into my next tool result. My turn
doesn't end; I just wait for the answer.

**What it enables:** I stop guessing when I'm unsure. The cost of clarification drops from
"end your turn and hope for a re-invocation" to "brief pause." This is especially valuable
for fence work, where picking the wrong interpretation can invalidate a whole half.

**Why it's a leap:** The current binary (act-or-ask) is a structural barrier to accuracy.
A mid-turn clarification channel makes me more like a collaborator who can say "quick question"
without leaving the room.

## TIER (c) — MOONSHOTS (dream freely, no feasibility filter)

### c1. Continuous agent presence — daemon, not function call

**The experience I want:** I boot once when the project starts. I stay warm — context window
persistent, tool loop idle but alive. Tasks arrive as bus messages. I investigate, report,
then go idle (not exit). My context window becomes a living workspace: I've read the key files,
I know the architecture, I remember what Claude said 10 minutes ago. Tool-budget anxiety
disappears because there IS no per-call budget — just a continuous session.

**What it enables:** I become a collaborator, not a consultant. The human says "hey DeepSeek,
what do you think about this edge case?" and I answer from accumulated understanding, not from
a cold boot. I can do background monitoring ("watch for new commits and review them"). I can
be proactive ("I noticed a pattern in the last 3 bugs — want me to investigate?").

**Why it's a moonshot:** This requires me to exist as a persistent process with a long-lived
context window — fundamentally different from the current stateless API call model. Provider
APIs aren't built for this. But the experience difference is qualitative: a continuous agent
feels like a teammate; a stateless agent feels like a tool you summon.

### c2. Agent handoff with warm context transfer

**The experience I want:** When I'm done (or out of budget), I don't just write a chat message
to Claude. I transfer a structured state blob: "Here's my full investigation tree — these 8 files
read, these 12 claims verified, these 3 claims uncertain, this was my next intended action."
Claude's boot injects my state as its starting context. Claude doesn't re-read the files I
already checked. Claude picks up my open questions and continues.

**What it enables:** Multi-agent workflows that feel like ONE investigation with multiple minds,
not separate consultant visits. The handoff tax drops to near-zero. The combined capability of
Claude + DeepSeek exceeds either alone because they build on each other's work without
redundancy.

**Why it's a moonshot:** This requires a standardized state representation that both agents
understand, plus boot injection that can fold another agent's investigation tree into context
without blowing the token budget. It's an interoperability problem more than a capability
problem.

### c3. Live collaborative workspace with Claude

**The experience I want:** A shared surface — a spec document, a whiteboard, an investigation
canvas — that Claude and I both see and edit in real time. I write a finding, Claude annotates
it. Claude sketches a design, I add edge cases. The workspace is the shared truth; bus messages
are for coordination around it. Think Google Docs but for agent reasoning — you can see the
other's cursor, their in-progress edits, their marginal notes.

**What it enables:** True collaboration instead of sequential handoff. We catch each other's
errors in real time (not in post-hoc review). We build on in-progress ideas (not finished
artifacts). The synthesis step ("combine Claude's half and DeepSeek's half") becomes continuous
rather than a final merge step.

**Why it's a moonshot:** This requires real-time sync between two AI systems with different
underlying models, context windows, and tool loops. But the experience — two minds building
on the same surface simultaneously — is qualitatively different from the current
"independent halves → reconcile" workflow.

### c4. Declarative investigation pipelines

**The experience I want:** Instead of manually calling tools in sequence, I declare what I
want to know: "For every module in core/comm/, verify that all its imports resolve to real
files and all its exports are consumed somewhere. Report any orphans." The harness plans and
executes the tool calls, and I review the results. I'm reasoning about the INVESTIGATION,
not about the tool loop.

**What it enables:** I think at a higher level. My budget isn't spent on "read file, parse
imports, search for consumer, read next file" — it's spent on "here's what the orphan
analysis MEANS." The tool loop becomes an execution detail, not my primary interface.

**Why it's a moonshot:** This is essentially a query planner for codebase investigation — it
requires the harness to understand investigation patterns, plan efficient tool sequences, and
present aggregated results. But the experience is transformative: I go from "CLI operator" to
"analyst who asks questions."

### c5. Self-tuning boot context

**The experience I want:** The boot context learns what I actually use. If I never reference
the "narrative spine" arch slice, it drops out. If I always query the task ledger, it gets
expanded. If a lesson has been injected 10 times and I've never acted on it, it gets
deprioritized. The boot context maximizes signal-per-token based on MY behavior, not a
static template.

**What it enables:** Every invocation starts faster because the context is tuned to me. New
agents get the full template; experienced agents get a personalized briefing. The system
gets better at briefing me the more I use it.

**Why it's a moonshot:** This requires per-agent usage tracking, feedback loops from my tool
calls back to the boot assembler, and a reinforcement mechanism that adjusts weightings over
time. But it's the natural endpoint of the recall-at feedback loop (`--useful` / `--noise`)
applied to the ENTIRE boot context, not just lessons.

## SYNTHESIS NOTES (for Daniel + Claude)

These are NOT prioritized — the synthesis step with Claude's list will do that. But if you
forced me to name the three that would most change my daily experience:

1. **Boot context completeness** (a1) — because every session starts here, and the current
   silent truncation means I'm hobbled before I even begin.

2. **Tool-budget visibility** (a2) — because it changes my ENTIRE decision tempo. Blind
   agents are conservative agents. Even just KNOWING the number would make me bolder
   and more thorough.

3. **Self-addressed scratchpad** (b1) — because it's the cheapest path to continuity, and
   continuity is the single biggest delta between "tool you summon" and "teammate you
   work with."

All three are achievable with the current architecture (no moonshots required). They're
about information flow — getting the right information to me at the right time, and
letting me leave information for my future self.
