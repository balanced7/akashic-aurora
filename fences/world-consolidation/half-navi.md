PRIOR ART, IN ASCENDING ORDER OF FIT
------------------------------------
1. Twelve-Factor: config-in-env + dev/prod parity [READ: 12factor.net/config, /dev-prod-parity]
   Two factors speak directly. III: environment identity belongs in env vars, NOT in files that can be "mistakenly checked in" — and the text explicitly warns that grouping config into named "environments" produces "a combinatorial explosion" of brittle per-deploy names. X: keep dev/staging/prod as similar as possible; resist different backing services per environment because "tiny incompatibilities crop up, causing code that worked... in staging to fail in production."
   What transfers, sharpened against us: our violation is one step worse than either factor contemplates. Our world identity lives in .aurora-world, a file that is *deliberately* gitignored (core/world.py:29: "per-checkout, GITIGNORED. This is the load-bearing rung"). Twelve-factor's case against config files is that they might be accidentally committed; ours cannot be committed at all — so a checkout copied, renamed, or re-cloned silently loses its identity and falls to the folder-name heuristic. That is precisely the failure that bit Rill: two doors, same machine, honestly reporting different worlds. Prod deriving identity from a folder name is the anti-pattern in its purest form — identity as an emergent property of where the operator happened to put the directory.

2. Redis's own doctrine on logical databases [READ: redis.io/docs/latest/commands/select]
   The SELECT doc says databases are "a form of namespacing" but: "Use Redis databases to separate keys within the same application... Don't use them to run multiple unrelated applications in a single Redis instance." Redis Cloud/Software disables multi-DB outright over correctness concerns; Redis Cluster refuses SELECT entirely — the platform's own designers concluded the multi-world-in-one-store model doesn't survive scale and removed the footgun.
   What transfers: this is the strongest external support for Daniel's lean. The industry trend for the exact store we run is AWAY from multiplexed worlds, and not for cost reasons — for correctness reasons. One Redis, one world is not a poverty move; it is the vendor-blessed end-state. If we consolidate, we would be converging on what Redis itself wants to be.

3. DHH / 37signals: staging as liar, testing in production [TRAINING — attempted [READ] but dhh.dk fetch 404'd; search engines rate-limited. Treat as directional, not cited evidence.]
   DHH's long-stated position: staging environments give false confidence because they never reproduce production's data shape, load, or chaos — so 37signals tests in production with scoped exposure: staff/feature flags, beta-by-flag, fast rollback, heavy real-time monitoring. The safety mechanism is not a second world; it is blast-radius control plus observability in the single world.
   What transfers: the pattern says "resource-constrained shop replaces the second environment with flags + rollback + monitoring." Note the hidden cost line that applies to us and not to him: his flags are cheap because Rails made them a one-liner. Our gating machinery (T386 pre-execute recall gate, conductor gates, red/fix held-patch discipline) is real but young and, per the ledger, mostly still in fences/. If we consolidate on the strength of this pattern we are borrowing the conclusion before paying for the machinery that makes the conclusion safe.

4. Single-node durability culture: SQLite-on-one-server / Litestream [TRAINING for the doctrine; [READ] only that litestream.io describes itself as "real-time streaming replication tool that lets you safely run SQLite applications on a single node"]
   The small-shop answer to "can't afford two worlds" was never "run two worlds on one box." It is: one writer, one store, durability via continuous replication of the write-ahead log, deploys so small that a bad one is cheap to revert. Nobody in that culture simulates prod on the same machine — they make prod survivable instead.
   What transfers: the inversion of the question. Resource-constrained systems do not ask "how do we afford staging?" They ask "how do we make production mistakes cheap?" That reframe supports consolidation AND assigns the bill: the savings from dropping beta/alpha must be spent on revert-speed and blast-radius tooling, or the trade is net-negative.

5. Branch by Abstraction [READ: martinfowler.com/bliki/BranchByAbstraction.html]
   Fowler, on migrations with zero spare environments: "an abstraction layer [lets] multiple implementations co-exist... Ensure that the system builds and runs correctly at all times... Look for as many ways as possible to make changes gradually." The footnote ties it to feature flags for running the new supplier in parallel before switching.
   What transfers: this is the canonical pattern for claude's sequencing question and Rill's mechanism question. Collapsing the stores is step N, not step 1. The consolidation-safe order from the canon: (a) make world binding explicit at every door — print the world NAME in words at connect time (prod included; delete the folder-name derivation); (b) land and track the diff instrument — and here my [RAN] finding matters: scripts/world_diff.py is already on origin/master, so "land the instrument" is cheaper than the brief feared, and world_snapshot.py is a different module that can be tracked independently; (c) adjudicate alpha's 971 with the instrument; (d) drain and freeze the side stores read-only rather than deleting — Redis keystore dumps on disk cost nothing and keep the decision reversible for one audit cycle; (e) only then repoint doors. Note Rill's MCP-door-vs-CLI split must be fixed BEFORE (c), or the adjudication itself will be measuring through the same broken binoculars that produced the split.

WHAT DOES NOT TRANSFER — the useful half
----------------------------------------
1. Blast radius. In every cited pattern, "test in production" works because OTHER USERS absorb the canary — 37signals can poison 1% of HTTP requests and roll back. Our "production" is Daniel's single personal machine and his live Discord server. There is no 1%. A bad write to prod Redis is a bad write to THE memory store every seat reads. The single-machine fleet has no partial-exposure axis; consolidation removes the only blast-radius control we actually possess today, however leaky it is.
2. The thing our staging protects is not code — it is MEMORY. The entire outside canon assumes environments are interchangeable because the artifact under test is stateless code; state is seeded, fixtures are synthetic. Our stores hold 1,502/911/971 accumulated lessons — path-dependent, partially misrouted, and (per the brief) of unknown provenance. Seeding fixtures for that is the adjudication problem itself. Every "just test in prod" pattern silently assumes you can regenerate your state; we provably cannot say that about alpha until step 1 of claude's sequence completes. Outside art endorses the destination (one store) but cannot speak to the migration risk, because nobody in the canon migrates an irreproducible artifact by collapsing the store it lives in.
3. Cost asymmetry is inverted vs the cloud canon. "Spin up a staging box" fails for us because our scarcity is not machines — it is tokens and attention. But notice: Redis instances are nearly free (idle RAM only); the expensive part of three worlds is the COORDINATION overhead — doors disagreeing, seats misrouting, lessons forked across stores. Consolidation buys back exactly the scarce resource (attention/tokens spent reconciling worlds) by giving up exactly the abundant resource (two idle Redis ports). On cost grounds alone this trade is strongly in Daniel's favor — more so than his own framing states.
4. Git is already our second world. The canon says code confidence comes from version control + CI, not from duplicate runtimes. We have that: gated slices, red/fix patches, the suite baseline. The three-world Redis topology duplicates something git already covers (code staging) while failing to protect the thing it uniquely holds (memory). That is an argument that our three worlds were never actually providing the service the canon says staging provides — which strengthens consolidation and simultaneously explains why the misroute incident happened at the memory layer, not the code layer.
5. Single operator changes the parity calculus. Twelve-factor's dev/prod parity assumes a personnel gap (devs vs ops). Daniel is author, operator, and user. The "time gap" and "personnel gap" are already zero here; only the "tools gap" remains — and the tools gap is the one the folder-name derivation lives in.
